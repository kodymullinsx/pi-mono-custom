# End Session Retrospective

Run evidence intake first, then all three phases in sequence. Low-risk domain memory and `_notes.md` updates may remain autonomous under the memory-creator workflow. Promotion into trusted instructions or behavior-changing files, including `SKILL.md` and `AGENTS.md`, requires explicit user approval before editing.

Pi-specific notes:
- Instruction file is `AGENTS.md` (not CLAUDE.md) — global at `~/.pi/agent/AGENTS.md`, project-level in repo root
- No native plan mode or background jobs in Pi — use `todo` tool for task tracking
- Memory routing is automatic via the `domain-memory` extension (same CWD logic as Claude)
- `_index.md` is auto-regenerated by the extension when `memory.md` is written — no manual regen needed
- The Pi memory ledger is observational only under `~/.pi/agent/memory/`; it may surface evidence but must not directly promote anything into trusted memory

## Phase 0 — Evidence Intake

Before deciding what to write, inspect the Pi ledger for evidence captured during the session:

- Route events under `~/.pi/agent/memory/events/` show what `domain-memory` routed, injected, fell back to, or suppressed.
- Friction candidates under `~/.pi/agent/memory/candidates/friction/` show lexical user corrections or preference signals. Treat these as evidence only.
- Compaction packets under `~/.pi/agent/memory/capture/compaction/` preserve user corrections, failed paths, decisions, and open loops from spans Pi compacted.
- Routing reports under `~/.pi/agent/memory/reports/routing/` are generated sidecars for review, not router configuration. The reporter prints dry-run JSON by default and writes sidecars only with `--write`.

Use the evidence to improve recall, then decide whether each item should become stable memory, a `_notes.md` session note, a skill/instruction proposal, or no action. Do not promote ledger evidence into `SKILL.md`, `AGENTS.md`, or other trusted instruction files without explicit approval.

## Phase 0.5 — Source Reconciliation

If the session involved a `~/work/` domain with a `_source-map.json` mapping, run the reconciler to detect drift between project source files and memory pointers:

```bash
node ~/.pi/agent/scripts/reconcile-memory-sources.mjs --domain <active-domain> --json
```

**Domain selection** (first match wins):
1. Domain explicitly named by user during session
2. Most recent `route_event.injected_domain` from the Pi memory ledger that maps to a `_source-map.json` entry
3. Most-specific `_source-map.json` sourceRoot match for session CWD

If no match is found, skip this phase.

**Handling findings:**
- `new_unindexed`: propose adding entries to `file-index.md` (or creating one if `reference_index_missing`). Route through normal memory-creator workflow in Phase 1.
- `stale_pointer`: propose removal from the referencing markdown file.
- `unmapped_artifact`: propose include/exclude recommendation for `_source-map.json` only; never silently expand scope.
- `memory_only_artifact` (reverse mode): propose whether the memory-held artifact should be copied into the project source folder, retained only in memory, or removed from memory. Do not copy/delete without user approval.
- `memory_divergent_artifact` (reverse mode): propose a human review of the memory artifact versus the source counterpart before replacing either version.
- `memory_artifact_unmapped` (reverse mode): propose whether the memory domain needs a `_source-map.json` entry or whether the artifact should remain memory-only.

Optionally run reverse mode for the active domain:
```bash
node ~/.pi/agent/scripts/reconcile-memory-sources.mjs --domain <active-domain> --reverse --json
```

**Dream interaction rule:**
- Pointer-only updates to `file-index.md` do not require Dream review and do not generate `_notes.md` entries.
- Any finding that implies a changed project state, new deliverable, missing evidence, or stale source should append a concise `_notes.md` item after approval:
  ```markdown
  <!-- YYYY-MM-DD session note -->
  - Source reconciliation found [description]. Review whether [relevant memory.md section] should change.
  ```
- Dream remains responsible for promoting `_notes.md` into `memory.md` during weekly review.

## Phase 1 — Memory Update

**Delegate to memory-creator skill.**

Scan the session for memory-worthy content (new facts, project state changes, decisions, corrections, contacts, deadlines). Then invoke the memory-creator skill with context about what changed.

The memory-creator skill handles:
- Routing to correct tree (`~/Workspace/Memory/` vs `~/work/Memory/`)
- Reading existing domains and applying autonomous edits
- Organizing content across memory.md and references/
- Updating last_updated and syncing _index.md

The `domain-memory` extension auto-regenerates `_index.md` on memory.md writes — no manual regen needed in interactive sessions.

**Enriched domain index sync:** The extension also triggers `~/.claude/bin/memory-drift-check.py` automatically when memory.md is written. However, if any domain was created or its `description:` frontmatter was changed outside a Pi write operation, run the script manually before closing the session:

```
python3 ~/.claude/bin/memory-drift-check.py
```

A domain absent from `enriched_domain_index*.json` will never be routed to by the BGE router, regardless of how correct `_index.md` and `memory.md` are.

### Two tiers of memory output

**Stable facts → `memory.md` directly** (current behavior). Use when the fact is confirmed and unlikely to change before the next Dream cycle.

**Session context → `_notes.md`** (append-only, per-domain). Use when content is real but session-specific, in-progress, or not yet stable enough for permanent inclusion. Dream reads `_notes.md` alongside `memory.md` during its weekly `review-domain` pass and promotes relevant content — then clears the file.

Format for `_notes.md` entries:
```markdown
<!-- YYYY-MM-DD session note -->
- [observation or context fragment]
```

When in doubt between the two tiers: if the fact would still be true and useful in a week, write it to `memory.md`. If it might be superseded by then, write it to `_notes.md`.

See: `memory-creator` skill at `~/.pi/agent/skills/memory-creator/SKILL.md` for full procedures.

## Phase 2 — Skill & Feedback Capture

**Step 1: Identify correction patterns**

Scan the session for moments where:
- User corrected your approach ("no", "don't", "wait", "actually", "stop", "not like that")
- User explicitly validated a non-obvious choice ("yes exactly", "perfect", "keep doing that")
- You made the same mistake twice
- A surprising approach turned out to be right

**Step 2: Determine scope**

For each pattern, decide:
- **Behavioral rule** → add to `~/.pi/agent/AGENTS.md` or auto-memory
- **Skill-specific** → update that skill's SKILL.md at `~/.pi/agent/skills/<name>/SKILL.md`
- **New skill warranted** → flag for user confirmation (don't create unilaterally)

**Step 3: Propose trusted changes before editing**

For durable behavior changes, summarize the evidence and ask for approval before editing `SKILL.md`, `AGENTS.md`, or creating a new skill. Low-risk memory notes may be written through the memory-creator workflow, but trusted procedural changes are approval-gated.

See: `skill-creator` skill at `~/.pi/agent/skills/skill-creator/SKILL.md` for creating/updating skills.

---

## Phase 3 — AGENTS.md Review

**Scan for structural gaps:** Check for friction pointing to missing or wrong instructions:
- Workflow rules that were forgotten or misapplied
- Tool preferences not yet codified
- Constraints that came up multiple times (provider role compatibility, extension availability, etc.)
- Pi-specific nuances that should be documented globally

**Apply targeted edits only after approval:** Make targeted insertions only; no restructuring. Trusted instruction edits require explicit user approval.

Read `~/.pi/agent/AGENTS.md` for context before editing.

---

## Todo Hygiene Check

Before declaring the session complete, review current todos owned in the session and clean up any that are stale:
- mark resolved work `completed`
- release items you are no longer actively owning
- do not leave finished or superseded work in `pending` / `in_progress`

If a todo remains open at session end, explicitly state why it is still open.

## Completion

After all three phases, summarize in 3–5 bullet points what was updated across memory, skills, AGENTS.md, and todo cleanup. Confirm session is ready to close.
