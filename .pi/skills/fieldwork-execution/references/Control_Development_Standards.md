# Control Development Standards

## Control Description Examples by Type

### Automated Configuration Control

**Pattern**: "[System] is configured to [objective] based on [parameter]. [Error handling]."

**Example 1 - Trading Authorization**:
"Calypso is configured to enforce authorization limits based on trader job class, preventing execution of any trade exceeding the configured threshold. Trades exceeding limits are automatically rejected with error messages to the Trading Operations team."

**Example 2 - Data Validation**:
"The Margin Library model is configured to validate input parameters against defined thresholds before performing margin calculations. Validation failures are systematically logged and escalated through automated alerts to the trading systems support team."

**Example 3 - SOD Enforcement**:
"Ariba is configured to prevent users from both creating and approving purchase orders within the same workflow. The system automatically blocks approval attempts for self-created orders with notification to the Procurement Manager."

### Automated Enforcement Control

**Pattern**: "[System] enforces [objective] by [mechanism]. [Error handling]."

**Example 1 - Segregation of Duties**:
"Migraph enforces segregation of duties by preventing users from both creating and approving vendor records within the same workflow. Override attempts are logged and escalated to management."

**Example 2 - Access Restrictions**:
"Workday enforces role-based access controls by restricting HR Technology personnel access to employee compensation data modification functions. Unauthorized access attempts generate immediate alerts to the Security Operations Center."

### ITDM (Semi-Automated) Control

**Pattern**: Describe both automated generation and manual review components.

**Example 1 - Reconciliation**:
"Monthly, the Finance Manager reviews the automated reconciliation exception report generated by the Alteryx workflow to identify variances exceeding $10,000 between source and target systems. The manager documents investigation results and resolution actions in the Reconciliation Tracking Log."

**Example 2 - Model Validation**:
"Annually, TCM uses internal and external inputs from upstream sources that are loaded into Polypaths to execute the Asset Liability Management model. A Python validation script performs automated data integrity checks post-execution, and Finance Risk Management reviews variance reports flagging discrepancies for investigation."

### Interface Control

**Pattern**: "The [Source] to [Target] interface transfers [data] via [method/frequency], with [validation]. [Error handling]."

**Example 1 - Pricing Data**:
"The Bloomberg to Calypso interface automatically transfers daily CUSIP pricing data through real-time API connections, with data validation checks to confirm completeness and accuracy of all transferred pricing fields. Validation failures result in automated error alerts to the Trading Operations team."

**Example 2 - Batch Transfer**:
"The LOS to CBS interface transfers approved loan data through nightly batch processing, with completeness and accuracy validation checks. Data integrity errors are logged and addressed daily by IT Operations."

### Manual Control

**Pattern**: "[Frequency], [Who] performs/reviews/approves [what]. [Documentation/evidence]."

**Example**:
"Monthly, the Finance Manager reviews the reconciliation exception report to identify variances exceeding $10,000 and documents investigation results in the Reconciliation Tracking Log."

### Monitoring Control

**Pattern**: "[System] monitors [activity/metric] and logs [details]. [Alert/escalation]."

**Example**:
"Control-M monitors all scheduled batch jobs and logs execution status, start/end times, and failure details. Failed jobs trigger immediate email alerts to IT Operations."

## Positive vs. Negative Testing Definitions

### Positive Testing
**Purpose:** Validates that the control allows legitimate transactions/data to be processed correctly.

**Approach:**
- Test with valid inputs that should be accepted
- Confirm the control does not inappropriately block legitimate activity
- Verify successful processing and expected outcomes

**Standard Test Step Language:**
```
Perform a positive test to validate that [control/validation checks] over [data type/process] 
operate as designed and the system only allows valid [data/transactions] to be [processed/ingested].
(Attribute B)
```

**Example:**
"Perform a positive test by executing a trade within authorized limits and confirm the system processes the transaction successfully."

### Negative Testing
**Purpose:** Validates that the control prevents invalid transactions/data from being processed.

**Approach:**
- Test with invalid inputs that should be rejected
- Confirm the control appropriately blocks illegitimate activity
- Verify rejection with appropriate error handling

**Standard Test Step Language:**
```
Perform a negative test to validate that [control/validation checks] over [data type/process] 
operate as designed and the system rejects invalid [data/transactions]. (Attribute C)
```

**Example:**
"Perform a negative test by attempting to execute a trade exceeding authorized limits and confirm the system rejects the transaction with appropriate error messaging."

### Combined Pattern
```
Perform a positive test to validate that validation checks over [data type] operate as designed 
and the system only allows valid data to be ingested. (Attribute B)

Perform a negative test to validate that validation checks over [data type] operate as designed 
and the system rejects invalid data. (Attribute C)
```

## Test Step Examples by Control Type

### Automated Configuration Control

```
Perform a walkthrough of the Calypso authorization configuration and inspect the trading limits framework to validate:
1. Inspect the authorization limit configuration to confirm that limits are systematically configured by trader job class with defined thresholds for each class. (Attribute A)
2. Perform a positive test by executing a trade within authorized limits and confirm the system processes the transaction successfully. (Attribute B)
3. Perform a negative test by attempting to execute a trade exceeding authorized limits and confirm the system rejects the transaction with appropriate error messaging. (Attribute C)
4. Validate that trades exceeding authorization limits generate automated error notifications to Trading Operations with sufficient detail for investigation. (Attribute D)
5. Inspect access controls to confirm only authorized Risk Management personnel can modify trader authorization limit configurations. (Attribute E)
6. Validate that authorization limit configuration changes follow the established change management process including testing and approval before implementation. (Attribute F)
```

### Interface Control

```
Perform a walkthrough of the Bloomberg to Calypso interface and inspect the API configuration to validate:
1. Inspect the API mapping schema to confirm all required pricing fields are transferred completely and accurately from Bloomberg to Calypso. (Attribute A)
2. Perform a positive test by submitting valid pricing data and confirm the system accepts and ingests it successfully into Calypso pricing tables. (Attribute B)
3. Perform a negative test by submitting incomplete pricing data and confirm the system rejects it with appropriate error messages identifying missing fields. (Attribute C)
4. Validate that validation failures are logged with sufficient detail including timestamp, CUSIP, and error type for investigation and remediation. (Attribute D)
```

### ITDM Control

```
Perform a walkthrough of the monthly reconciliation process and inspect reconciliation documentation to validate:
1. Inspect the Alteryx workflow configuration to confirm the automated reconciliation logic compares source and target data with defined variance thresholds. (Attribute A)
2. Validate that the automated reconciliation report is generated on schedule and contains all required data elements for management review. (Attribute B)
3. Inspect evidence of management review including documented variance investigation and resolution for exceptions exceeding the $10,000 threshold. (Attribute C)
4. Validate that unresolved reconciliation exceptions are escalated according to defined procedures with appropriate management notification. (Attribute D)
```

### Manual Control

```
Perform a walkthrough of the approval process and inspect approval documentation to validate:
1. Inspect the approval workflow to confirm the appropriate level of authority reviews and approves transactions based on dollar thresholds. (Attribute A)
2. Validate that approval evidence includes documented review of key transaction details including vendor, amount, and business justification. (Attribute B)
3. Confirm that approved transactions are processed timely within defined service level agreements. (Attribute C)
4. Validate that approval authority matrices are current and align with organizational structure and delegation of authority policies. (Attribute D)
```

## DA Team Cross-Reference Patterns

### For Integrated Testing Coverage
Use when IT and DA teams have complementary testing scopes:
```
IAD Note: For full coverage over the completeness and accuracy of the [process/interface/data], 
refer to test procedures performed by the Data Analytics team within [Control Name] in MyGRC.
```

### For Exception Supporting Evidence
Use when DA testing provides additional evidence for an identified exception:
```
For additional supporting evidence regarding the exception, refer to the data analytics testing 
(Workpaper_XXXXXX).
```

### For Scope Delineation
Use to clarify testing responsibilities between IT and DA teams:
```
Note: Testing by the integrated team will be focused on [IT scope - e.g., configuration validation, 
code inspection, system controls]. The DA team will test [DA scope - e.g., data completeness, 
calculation accuracy, population reconciliation]. Refer to [Control Reference] for details.
```

### For Downstream Testing Reference
Use when testing feeds into another control:
```
For testing over the downstream manual review and approval of [output] generated by this 
[workflow/script], refer to [Control Name].
```

### For Input/Output Validation
Use when multiple controls cover end-to-end data flow:
```
For testing over the accuracy and reconciliation of [input source] data, refer to [Control Name]. 
For testing over the [downstream process], refer to [Control Name].
```

## Developing Control Variations

When users request multiple variations of a control description, generate 3 options showing different approaches:

### Variation Dimensions
1. **Length**: Minimal (1 sentence) → Standard (2 sentences) → Detailed (3 sentences)
2. **Focus**: System-centric → Process-centric → Outcome-centric
3. **Error Handling**: Implicit → Explicit logging → Multi-tier response
4. **Technical Detail**: High-level → Moderate → Detailed

### Example: Semi-Automated to Automated Conversion

**Original (Semi-Automated)**:
"Annually, Finance Risk Management performs interest rate quality checks to validate that Polypaths scenarios match CST scenarios. A Python script performs data validation post-execution."

**Variation 1 - Minimal**:
"The Python validation script performs automated data integrity checks comparing Polypaths interest rate scenarios to CST scenarios, with variances flagged for investigation."

**Variation 2 - Standard (Recommended)**:
"The Python validation script validates that interest rate scenarios processed through Polypaths match the CST scenario by performing automated data integrity checks post-execution of the Asset Liability Management model. Variances exceeding defined thresholds are logged and trigger automated alerts to Finance Risk Management."

**Variation 3 - Detailed**:
"The ALM model execution process incorporates an automated Python validation script that systematically compares Polypaths interest rate scenarios against CST scenario inputs for completeness and accuracy. The script performs post-execution data integrity checks including scenario parameter validation, rate curve comparison, and threshold compliance verification, with variances exceeding 5 basis points logged to the validation error table and automated email alerts sent to Finance Risk Management for investigation."

## Common Pitfalls to Avoid

### 1. Over-Engineering Control Descriptions
**Problem**: Exceeding 3 sentences with excessive detail
**Solution**: Focus only on core mechanism, what is controlled, and error handling

### 2. Generic System References
**Problem**: Using "the system" instead of specific names
**Solution**: Always use actual system names (Calypso, Migraph, Workday)

### 3. Passive Voice
**Problem**: "Data validation is performed by..."
**Solution**: "The LOS validates data completeness..."

### 4. Missing Error Handling
**Problem**: "Calypso validates trade settlement data."
**Solution**: "Calypso validates trade settlement data before GL posting. Validation failures result in automated error alerts."

### 5. Vague Test Steps
**Problem**: "Inspect the system configuration."
**Solution**: "Inspect the Calypso authorization configuration to verify that limits are systematically configured by trader job class with defined thresholds."

### 6. Using "Ensure"
**Problem**: "The system ensures data quality..."
**Solution**: "The system validates data quality..."

### 7. Excessive Supplemental Question Answers
**Problem**: Multi-sentence paragraphs for each supplemental question
**Solution**: Limit to 1-2 sentences (ITDM exception: 3) per answer; expand only when essential

### 8. Using "because" in workpaper documentation
**Problem**: "The control design is not adequate to mitigate data integrity risk because..."
**Solution**: Replace with "as," "given that," "in that," or restructure — "because" is informal and out of place in workpaper writing

### 9. Em dashes or en dashes in workpaper text
**Problem**: "The Treasury team — based on job titles — possesses requisite expertise..."
**Solution**: Integrate naturally or use parentheses: "The Treasury team (whose members possess requisite expertise based on job titles)..."

## Attribute F: Change Management for Vendor/Role-Based Controls

When testing Attribute F (Change Management) for a vendor-hosted application that enforces authorization through hard-coded logic rather than a configurable routing engine, the write-up structure differs from configurable controls. The authorization workflow itself is fixed in vendor code; the only configurable surface subject to change management is the role configurations and their associated parameters.

**Four-part structure:**

1. **Establish the architecture** — state that the authorization logic is hard-coded vendor application logic (not routing-based), and that any user holding the requisite role-based parameters may progress through the workflow. This frames why configuration inspection, not routing table analysis, is the appropriate test approach.

2. **Identify what is configurable** — state that the only elements subject to change management are the roles themselves and their associated parameter restrictions (limits, privilege flags, etc.).

3. **Document governance of those configurations** — identify who manages them (business team or IT team), and what cadence or trigger governs updates (e.g., tied to an annual supervisory plan review cycle, a corporate policy update, or a formal change request).

4. **Confirm LMDs align and change management documentation supports** — state that last modified dates in the configuration report are consistent with the documented update window, and that corresponding change management documentation was inspected and found appropriate.

**Example — Vendor Application with Role-Based Authorization (EPP):**
```
To validate that changes to EPP authorization configuration followed the standard change
management process, and to confirm our understanding, IAD inquired with [IT Contact] and
[Business Contact]. Per inquiry, IAD noted that EPP enforces authorization controls through
hard-coded vendor application logic rather than a configurable routing engine; as designed,
any user holding the requisite role-based approval limit may advance a wire transaction
through the authorization workflow. The only configurable elements subject to change
management are the roles themselves and their associated approval limit restrictions.

Per inquiry with [Business Contact], the EPP authorization roles and associated approval
limits are business-managed by [Team] and are updated in accordance with [governing cadence,
e.g., the annual Written Supervisory Plan review cycle (Cntl_XXXXXX)]. The most recent
update to the authorization configuration occurred in [timeframe], coinciding with [trigger
event]. Based on inspection of the last modified dates within the [report name] (Exhibit X,
Tab X), IAD confirmed that the configuration changes logged during the audit period are
consistent with the [timeframe] update window and aligned with appropriate change management
documentation. Therefore, IAD gained comfort that EPP authorization configuration changes
followed the standard change management process. Attribute F satisfied, no exceptions noted.
```
